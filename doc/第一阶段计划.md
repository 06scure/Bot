# 桌面 AI 机器人第一阶段计划

> 更新时间：2026-09-14

## 1. 阶段目标

在鲁班猫 2 上完成一个可运行、可测量、可复现的端侧闭环：检测到人进入工位 ROI 后，使用 RKNN 加速的 MeloTTS 播报一次中文问候；中文模型同时支持中英混读。

```text
OV8858 摄像头
  -> V4L2 / OpenCV 取帧
  -> RGA 缩放与颜色转换
  -> RKNN YOLOv8n 人体检测
  -> 工位 ROI 与连续帧确认
  -> 到岗状态机
  -> MeloTTS RKNN 推理
  -> ALSA 播放问候语
```

## 2. 第一阶段技术栈

| 层次 | 技术 |
|---|---|
| 语言与构建 | C++20、CMake、CTest |
| 系统 | Linux、多线程、systemd、journald |
| 摄像头 | V4L2、OpenCV |
| 图像加速 | RGA |
| 模型推理 | RKNN-Toolkit2、RKNPU2、YOLOv8n INT8 |
| 语音合成 | RKNN MeloTTS |
| 音频输出 | ALSA（板载 RK809，SPK/HP 输出） |
| 服务接口 | cpp-httplib、nlohmann/json |
| 日志与测试 | spdlog、GoogleTest 或 Catch2 |


## 3. 运行架构

采用单进程、模块化、多线程架构。线程之间使用有界队列传递数据，生产端允许丢弃旧帧，TTS 请求不得无限积压。

```text
CaptureThread
  -> RGA Preprocessor
  -> PerceptionThread
  -> TriggerEngine
  -> SkillExecutor
  -> TtsWorker
  -> ALSA

HttpServer 独立监听状态、事件和手动触发请求。
```

## 4. 模块与接口

| 模块 | 职责 | 核心接口 |
|---|---|---|
| capture | 摄像头取帧 | `IFrameSource` |
| preprocess | 缩放、裁剪、旋转和格式转换 | `IPreprocessor` |
| vision | RKNN 推理与后处理 | `IDetector` |
| trigger | ROI、连续帧和冷却判断 | `ITriggerPolicy` |
| skill | 技能执行 | `ISkill` |
| tts | MeloTTS 完整推理，并管理音频缓存 | `ITextToSpeech` |
| audio | ALSA 播放 | `IAudioSink` |

技能标识为 `greet_at_desk`，同一到岗过程不得重复播放。

## 5. 检测与触发默认值

```json
{
  "model": "yolov8n_person.rknn",
  "input_size": 416,
  "precision": "int8",
  "roi": [0.15, 0.25, 0.85, 0.95],
  "min_score": 0.60,
  "min_consecutive_frames": 5,
  "absence_reset_ms": 1000,
  "cooldown_ms": 600000
}
```

RGA 是主要预处理路径，不可用时回退到 OpenCV CPU。状态机为 `ABSENT -> PERSON_CANDIDATE -> PRESENT -> GREETED -> COOLDOWN -> ABSENT`，人体框中心进入 ROI 且连续五帧满足置信度后触发。

## 6. MeloTTS 与音频

### 6.1 选型结论

原 MMS-TTS 方案只能覆盖英文问候：MMS 官方语言覆盖表中普通话有 ASR/LID，但没有正式 TTS 模型。MeloTTS 中文模型明确支持中英混读，野火已提供从 PyTorch/ONNX 导出、RKNN 转换到 C++ 板端部署的完整链路，并在转换脚本中列出 `rk3566`、`rk3568` 等目标平台。因此改用 MeloTTS。

野火教程的 `1.341 s` 是 RK3588 上一次完整推理的外层计时，包含逐句音素转换、encoder、middle process 和 decoder，不包括模型初始化、lexicon 初始化与首次句子切分；对应 5.596 s 音频，RTF 约 0.240。RK3568 仅在转换目标支持列表内，教程没有给出该板实测值，所以必须在阶段一的平台验证中做硬性门禁：若中文音质或完整合成延迟不可接受，则回退到预置问候音频，或另选轻量中文 TTS 后重新评估，不把 RK3588 数据外推为 RK3568 指标。

野火当前 RKNN 转换脚本的量化路径为 `fp`（FP16），不是 YOLOv8n 使用的 INT8；因此 RK3568 的内存占用、完整合成延迟与持续运行稳定性必须实板测量，不能沿用 INT8 模型的性能假设。

MeloTTS 代码与中文权重标注为 MIT 许可，允许商业和非商业使用。第一阶段仅使用中文模型并关闭 BERT 推理，不引入额外的 BERT RKNN 模型。

### 6.2 模型边界与调用关系

MeloTTS 基于 VITS。为了适配 RKNN 对动态形状算子的限制，一次完整的 TTS 推理被拆成 encoder、C++ 中间处理和 decoder 三段：

```text
固定中文或中英混合问候语
  -> MeloTTS C++ 文本前端（句子切分、标点规范化、lexicon/tokens；运行时不依赖 Python/Jieba）
  -> encoder.rknn：音素、声调、语言、说话人与零 BERT 特征 -> 时长、先验均值与先验方差等
  -> C++ middle process：时长展开、掩码与对齐中间表示
  -> decoder.rknn：中间表示 -> 44.1 kHz 单声道波形
  -> PCM/WAV 缓存
  -> ALSA 播放
```

encoder 与 decoder 是同一次合成的前后两段，中间的时长展开与对齐必须在 C++ 中完成，三者必须成对使用。野火示例采用常驻内存的 `lexicon.txt` 与 `tokens.txt` 完成文本前端，约 7.1 MB 的 `lexicon.txt` 在 RK3588 上初始化约 554 ms；服务应在启动时加载一次并复用。

野火 C++ 文本前端不是通用 G2P，而是面向固定词典的音素/声调查找；未命中的中文或英文 token 会回退为空白，可能造成漏读。因此第一阶段默认问候语必须逐词存在于提供的 `lexicon.txt` 中，并在验收时人工听检；后续若要支持开放词汇动态文本，需要补充分词、英文 G2P 或启用 BERT 路线后再单独验证。

野火部署代码固定 `MAX_LENGTH=256`，decoder 最大输出为 `512 x 512 = 262144` 个采样点；按 44.1 kHz 计算约 5.94 s。问候文本必须保持简短或按句切分，任一分片不得超过模型上限，否则会被截断。野火示例本身是一次性 CLI（启动、推理、保存、退出），我们的服务只复用其文本前端和 RKNN 推理代码，并把模型上下文改造成常驻服务。

### 6.3 第一阶段运行策略

- 启动时加载文本前端、encoder 与 decoder 并常驻，避免每次触发重新初始化。
- 默认问候语固定为 `早上好，欢迎回来。Let's have a productive day.`；启动后执行一次完整 TTS 合成，记录冷启动耗时，并缓存为 44.1 kHz 单声道 WAV 或 PCM。
- 音频缓存采用“文本 -> 音频”映射，而不是写死 WAV：缓存命中时直接播放；未命中时执行完整 TTS，成功后写入缓存。第一阶段问候语固定，启动时走一次未命中合成，后续到岗触发均命中缓存。
- 人员到岗触发后优先播放缓存音频，不重复运行 TTS 推理；这样可避免合成延迟阻塞到岗响应，并减少 NPU 占用与延迟抖动。
- 这不是禁止动态语音。若后续问候内容需要变化，仍走同一条“未命中则合成、命中则播放”路径；但当前 MeloTTS 部署不是流式 TTS，必须等 decoder 生成完整波形后才能开始播放。
- 缓存键至少包含问候文本、语言、说话人、语速、模型版本、lexicon/tokens 版本和采样率。任一内容变化时重新执行 encoder -> middle process -> decoder。
- TTS 初始化或推理失败时，播放随程序部署的预置 WAV，并在健康状态和事件日志中标记回退；预置音频必须与主路径保持相同的采样率和声道数。
- 音频通过 ALSA 输出。板载音频处理器为 Rockchip RK809，Linux 声卡通常为 `card 1`；默认播放路径为 `SPK`，无源扬声器连接板载 SPK 接口，规格为 8 Ω、额定功率 1 W。

## 7. 本地 HTTP 接口

| 方法与路径 | 作用 |
|---|---|
| `GET /health` | 查询进程、摄像头、RKNN、TTS 缓存和音频状态 |
| `GET /state` | 查询当前状态机状态 |
| `GET /events` | 查询最近事件 |
| `POST /skills/greet_at_desk` | 手动触发问候 |
| `POST /config/reload` | 重新加载非安全相关配置 |

服务默认只监听本机或局域网，不暴露到公网。

## 9. 开发顺序

1. 平台验证：摄像头、NPU、RGA、ALSA 和野火 MeloTTS C++ 示例全部跑通；在 RK3568 上分别记录峰值内存、文本前端初始化、encoder、middle process、decoder、完整合成和冷启动耗时；只有在中文/中英混读可懂、无截断且缓存命中后的播放启动延迟可接受时，才将 MeloTTS 定为第一阶段 TTS 栈。
2. C++ 骨架：CMake、线程、配置、日志、事件和技能接口。
3. 视觉闭环：摄像头、RKNN、ROI、状态机和冷却控制。
4. 语音闭环：文本前端与模型常驻、encoder -> middle process -> decoder 完整合成、中英混读、音频缓存、ALSA 播放和失败回退。
5. 稳定性：systemd、异常恢复、性能测试和文档。

## 10. 验收标准

1. 程序在鲁班猫 2 上正常运行，无网络时完成全部流程。
2. 人体进入工位后只问候一次，冷却期间不重复。
3. 离开工位后状态能够正常复位。
4. RKNN、RGA、OpenCV、MeloTTS 文本前端/encoder/decoder 与主机侧中间处理、ALSA 和 cpp-httplib 均进入运行链路。
5. 连续运行 1 小时无崩溃、无明显内存增长。
6. 提供 FPS、检测推理延迟、文本前端初始化、encoder、middle process、decoder、TTS 完整冷启动延迟和缓存命中后的播放启动延迟。
7. 提供硬件连接、构建、部署和调试说明。
8. 中文或中英混合问候能够完整播放且无截断，44.1 kHz 音频通过 ALSA 正常输出。
