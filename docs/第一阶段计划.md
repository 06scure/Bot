# 桌面 AI 机器人第一阶段计划

> 更新时间：2026-09-24

## 1. 阶段目标

在鲁班猫 2 上完成一个可运行、可测量、可复现的端侧闭环：检测到人进入工位 ROI 后，使用 RKNN 加速的 MeloTTS 播报一次中文问候；中文模型同时支持中英混读。

```text
OV8858 摄像头
  -> V4L2 取帧
  -> RGA 缩放与颜色转换
  -> RKNN YOLO26n 人体检测
  -> 工位 ROI 与连续帧确认
  -> 到岗状态机
  -> MeloTTS RKNN 推理
  -> ALSA 播放问候语
```

先完成独立的视觉里程碑：图片检测、摄像头连续检测、工位事件；以标注图和日志验收后再接语音。实现工作在实际开发环境中开展，本文不代表模型或硬件已验证。

## 3. 运行架构

### 3.1 线程模型

```text
main 线程
  加载配置 -> 装配 -> 启动后台线程 -> 阻塞托管 HTTP 监听
  -> 收到停止信号后按序关停

vision 线程
  V4L2 取帧 -> RGA 缩放与格式转换 -> RKNN YOLO26n 推理 -> 后处理
  -> DeskStateMachine -> GreetAtDeskSkill（产出 TTS 请求）

tts 线程
  TTS 请求队列 -> 命中缓存则直接播放，未命中则执行 encoder -> middle process -> decoder 并写入缓存
  -> ALSA 播放

HTTP 接口在 main 线程上监听。
```

- 采集与推理先放在同一线程，不设应用层帧队列；驱动仍可能积压缓冲，必须记录帧时间戳与帧龄，按实测决定丢弃旧帧的策略。
- 唯一的线程间队列是 TTS 请求队列，容量 1~2。问候语固定，重复请求没有意义，队列满时丢弃并记事件。
- `main` 阻塞在 HTTP 监听上。停止信号通过安全的通知机制交给正常线程，由正常线程调用 `stop()` 让监听返回，再按序停止 vision 与 tts 线程、释放 RKNN 上下文；信号处理器不直接调用 HTTP、日志或锁操作。
- 线程的创建、停止顺序和异常传播全部集中在 `app/`。

视觉里程碑只运行采集、推理与状态判断，不依赖 TTS 或 HTTP；以上线程拓扑在完整闭环时装配。

### 3.2 性能预期与承压分布

| 环节 | 由谁承担 | 对 A55 的负载 |
|---|---|---|
| V4L2 取帧 | DMA + CPU | 很低 |
| RGA 缩放与格式转换 | RGA | 低，调用与同步开销需实测 |
| YOLO26n 推理 | NPU | 低，主要是驱动开销 |
| YOLO26 后处理（解码、筛选、坐标还原） | CPU | 需实测，配套检测代码不执行 NMS |
| 图像拷贝（RGA 输出到 RKNN 输入） | CPU 与内存带宽 | 中等，随分辨率上升 |
| 状态机 | CPU | 忽略不计 |
| MeloTTS 文本前端 | CPU | 一次性，lexicon 加载约数百毫秒 |
| MeloTTS encoder 与 decoder | NPU | 低 |
| middle process（时长展开与对齐） | CPU | 中等，仅在缓存未命中时执行 |
| ALSA 播放 | CPU | 低 |

- 先采用单进程，按分段耗时定位瓶颈，再决定是否调整；Mali-G52 GPU 在这条链路中不参与。
- 更可能的瓶颈是内存带宽：A55、RGA 与 NPU 共享 LPDDR，分辨率提高或图像拷贝增多会先在这里吃紧。
- 其次关注 NPU 争用：MeloTTS 与 YOLO 共享 NPU，合成对视觉延迟的影响需实测。启动时合成一次并缓存，把这次争用整体移出运行期。
- 真正可能成为 CPU 热点的是 YOLO 后处理与图像拷贝，代价取决于实现：使用固定缓冲、预分配与索引访问，避免每帧的深拷贝与动态分配。
- 调度说明：Linux 的调度单位是线程而非进程，默认不做核绑定，两个后台线程由调度器分配到 4 个核中的任意核并在负载变化时迁移。"视觉线程占一个核"指它占用约一个核的算力，不是固定绑定在某个核上；只有在实测出现抖动或相互干扰时才考虑设置 CPU 亲和性。
- 确认方法：`pidstat -t -p <pid> 1` 观察每线程占用，配合各阶段耗时打点，即验收标准第 6 条要求的指标。

## 4. 模块划分与代码组织

代码按功能点划分，不按线程划分。判断依据是"会不会因为同一个理由修改"：同一个理由放在同一个文件，两个理由拆成两个文件。线程属于运行时拓扑，集中实现在 `app/` 这一处组合根；模块本身是可以被任意线程调用的普通类，模块内部不出现 `std::thread`。

| 模块 | 职责 | 主要类型 |
|---|---|---|
| app | 组合根：线程、有界队列、装配、生命周期、配置、事件日志 | `App`、`Config`、`EventLog` |
| capture | V4L2 取帧，RGA 缩放、裁剪与格式转换 | `V4l2FrameSource`、`RgaPreprocessor` |
| vision | RKNN 加载、YOLO26n 推理与后处理 | `YoloDetector` |
| trigger | ROI、连续帧、冷却与到岗状态机（纯逻辑） | `DeskStateMachine` |
| skill | 技能执行 | `GreetAtDeskSkill` |
| tts | MeloTTS 完整推理与音频缓存 | `MeloTts`、`AudioCache` |
| audio | ALSA 播放 | `AlsaPlayer` |
| http | 本地 HTTP 接口 | `HttpServer` |

约定：

- 不预设抽象基类。`capture`、`vision`、`tts`、`audio` 各只有一个实现，直接写具体类，不引入 `I` 前缀的接口层。
- 唯一的测试接缝是触发状态机：它只接收普通结构体（检测结果与时间戳），不引用 `opencv2`、`rknn_api.h`、`asoundlib.h`，以便在开发主机上脱离板卡单测。
- 技能标识为 `greet_at_desk`，同一到岗过程不得重复播放。

### 视觉线程的拆分条件

第一阶段把采集与推理放在同一线程。出现以下情况时才拆分：

- 推理负载上升：输入尺寸提高或引入第二个模型，单轮耗时超过帧间隔，帧率降到 10 以下，连续帧确认的延迟开始可被感知。
- 低延迟优先于帧率：要求推理期间持续取帧并始终处理最新帧。
- 采集需要独立节拍：增加录像或推流，采集必须保持恒定帧率。

拆分的前提是现在守住写法纪律：采集只负责返回下一帧，不持有推理状态；推理保持纯粹，不共享采集状态；状态机自己持有全部状态。满足这些条件时，拆分就是在 `app/` 中把两次调用分配到两个线程并在中间插入容量 1 的队列，模块本身无需改动。容量 1 的缓冲采用新帧覆盖旧帧，仍需测量驱动排队与线程调度延迟，不能据此保证延迟最多一帧。

## 5. 检测与触发默认值

```json
{
  "model": "yolo26n_rk3568_i8.rknn",
  "input_size": 640,
  "precision": "int8",
  "roi": [0.15, 0.25, 0.85, 0.95],
  "min_score": 0.60,
  "min_consecutive_frames": 5,
  "absence_reset_ms": 1000,
  "cooldown_ms": 600000
}
```

以上是待实板验证的起点。先用 640 建立正确性基线，再按效果与耗时比较 416/320；更改尺寸需要重新导出、转换和验证模型，不能只改配置。连续五帧的确认延迟随实际 FPS 变化，实测后再决定是否改为持续时间加最少有效帧数。

### 5.1 模型与预处理

- 参考[野火 YOLO26 教程](https://doc.embedfire.com/linux/rk356x/Ai/zh/latest/lubancat_ai/example/yolo26.html)，固定配套导出源码、权重、后处理和 RKNN 工具版本。开发主机完成 ONNX → RKNN，目标为 `rk3568`、batch 为 1，先验证 INT8；不外推 RK3588 性能。
- 先使用预训练多类别模型，仅在后处理中保留 `person`；这不减少网络本身的 NPU 计算。量化校准使用有代表性的场景图片，另留工位图片验收坐姿、背光和遮挡效果。
- 启动时校验输入输出张量的数量、尺寸、布局和类型；不匹配则报错。复用成套 YOLO26 解码，不套用 YOLOv8 后处理。
- RGA 完成颜色转换、等比例缩放和补边，保存实际缩放比例及补边量。核对颜色顺序、像素格式、步幅、对齐和归一化方式，避免重复归一化或静默 CPU 回退。
- 检测框先还原到原图，裁剪越界框、过滤非法数值和无效矩形，再归一化到 `[0,1]`，遵循 `src/vision/detection.hpp` 的约定；ROI 使用同一坐标系。
- 先明确采集、RGA、RKNN 缓冲区的所有权与释放时机，复用固定缓冲；零拷贝优化留到实测发现需要时。

### 5.2 工位判断与故障

人体框中心进入 ROI 且连续五帧达到阈值后确认在场；短暂漏检不复位，持续离开后允许下一次到岗。问候资格与在场事实分开，离开不清除冷却，冷却结束但人仍在场时不补播。

采集或推理失败必须单独报告，不能用空检测结果表示“无人”。RGA 是唯一的预处理路径，初始化或运行失败即记录错误并停止视觉链路，不做 CPU 回退。视觉里程碑只记录到岗事件，不模拟语音执行成功。

## 6. MeloTTS 与音频

### 6.1 选型结论

原 MMS-TTS 方案只能覆盖英文问候：MMS 官方语言覆盖表中普通话有 ASR/LID，但没有正式 TTS 模型。MeloTTS 中文模型明确支持中英混读，野火已提供从 PyTorch/ONNX 导出、RKNN 转换到 C++ 板端部署的完整链路，并在转换脚本中列出 `rk3566`、`rk3568` 等目标平台。因此改用 MeloTTS。

野火教程的 `1.341 s` 是 RK3588 上一次完整推理的外层计时，包含逐句音素转换、encoder、middle process 和 decoder，不包括模型初始化、lexicon 初始化与首次句子切分；对应 5.596 s 音频，RTF 约 0.240。RK3568 仅在转换目标支持列表内，教程没有给出该板实测值，所以必须在阶段一的平台验证中做硬性门禁：若中文音质或完整合成延迟不可接受，则改用预置问候音频，或另选轻量中文 TTS 后重新评估，不把 RK3588 数据外推为 RK3568 指标。该门禁是阶段选型决策，不是运行期代码分支。

野火当前 RKNN 转换脚本的量化路径为 `fp`（FP16），不是 YOLO26n 使用的 INT8；因此 RK3568 的内存占用、完整合成延迟与持续运行稳定性必须实板测量，不能沿用 INT8 模型的性能假设。

MeloTTS 代码与中文权重标注为 MIT 许可，允许商业和非商业使用。第一阶段仅使用中文模型并关闭 BERT 推理，不引入额外的 BERT RKNN 模型。

### 6.2 模型边界与调用关系

MeloTTS 基于 VITS。为了适配 RKNN 对动态形状算子的限制，一次完整的 TTS 推理被拆成 encoder、C++ 中间处理和 decoder 三段：

```text
固定中文或中英混合问候语
  -> MeloTTS C++ 文本前端（句子切分、标点规范化、lexicon/tokens；运行时不依赖 Python/Jieba）
  -> encoder.rknn：音素、声调、语言、说话人与零 BERT 特征 -> 时长、先验均值与先验方差等
  -> C++ middle process：时长展开、掩码与对齐中间表示
  -> decoder.rknn：中间表示 -> 44.1 kHz 单声道波形
  -> PCM/WAV 缓存
  -> ALSA 播放
```

encoder 与 decoder 是同一次合成的前后两段，中间的时长展开与对齐必须在 C++ 中完成，三者必须成对使用。野火示例采用常驻内存的 `lexicon.txt` 与 `tokens.txt` 完成文本前端，约 7.1 MB 的 `lexicon.txt` 在 RK3588 上初始化约 554 ms；服务应在启动时加载一次并复用。

野火 C++ 文本前端不是通用 G2P，而是面向固定词典的音素/声调查找；未命中的中文或英文 token 会回退为空白，可能造成漏读。因此第一阶段默认问候语必须逐词存在于提供的 `lexicon.txt` 中，并在验收时人工听检；后续若要支持开放词汇动态文本，需要补充分词、英文 G2P 或启用 BERT 路线后再单独验证。

野火部署代码固定 `MAX_LENGTH=256`，decoder 最大输出为 `512 x 512 = 262144` 个采样点；按 44.1 kHz 计算约 5.94 s。问候文本必须保持简短或按句切分，任一分片不得超过模型上限，否则会被截断。野火示例本身是一次性 CLI（启动、推理、保存、退出），我们的服务只复用其文本前端和 RKNN 推理代码，并把模型上下文改造成常驻服务。

### 6.3 第一阶段运行策略

- 启动时加载文本前端、encoder 与 decoder 并常驻，避免每次触发重新初始化。
- 默认问候语固定为 `早上好，欢迎回来。`；启动后执行一次完整 TTS 合成，记录冷启动耗时，并缓存为 44.1 kHz 单声道 WAV 或 PCM。
- 音频缓存采用“文本 -> 音频”映射，而不是写死 WAV：缓存命中时直接播放；未命中时执行完整 TTS，成功后写入缓存。第一阶段问候语固定，启动时走一次未命中合成，后续到岗触发均命中缓存。
- 人员到岗触发后优先播放缓存音频，不重复运行 TTS 推理；这样可避免合成延迟阻塞到岗响应，并减少 NPU 占用与延迟抖动。
- 这不是禁止动态语音。若后续问候内容需要变化，仍走同一条“未命中则合成、命中则播放”路径；但当前 MeloTTS 部署不是流式 TTS，必须等 decoder 生成完整波形后才能开始播放。
- 缓存键至少包含问候文本、语言、说话人、语速、模型版本、lexicon/tokens 版本和采样率。任一内容变化时重新执行 encoder -> middle process -> decoder。
- TTS 初始化或推理失败时不降级播放备用音频，而是记录错误并在 `/health` 与事件日志中标记；失败状态必须与"未触发"可区分。
- 音频通过 ALSA 输出。板载音频处理器为 Rockchip RK809，Linux 声卡通常为 `card 1`；默认播放路径为 `SPK`，无源扬声器连接板载 SPK 接口，规格为 8 Ω、额定功率 1 W。

## 7. 本地 HTTP 接口

| 方法与路径 | 作用 |
|---|---|
| `GET /health` | 查询进程、摄像头、RKNN、TTS 缓存和音频状态 |
| `GET /state` | 查询当前状态机状态 |
| `GET /events` | 查询最近事件 |
| `POST /skills/greet_at_desk` | 手动触发问候 |
| `POST /config/reload` | 重新加载非安全相关配置 |

服务默认只监听本机或局域网，不暴露到公网。

## 8. 代码结构

```text
src/
  main.cpp
  app/          App、Config、EventLog；线程、队列与装配集中在此
  capture/      V4l2FrameSource、RgaPreprocessor
  vision/       YoloDetector
  trigger/      DeskStateMachine（纯逻辑，可脱离硬件测试）
  skill/        GreetAtDeskSkill
  tts/          MeloTts、AudioCache
  audio/        AlsaPlayer
  http/         HttpServer
  util/         有界队列、日志封装
config/  models/  tests/  scripts/  docs/  third_party/
```

`third_party/` 存放 vendor 进来的 spdlog、Catch2、cpp-httplib 与 nlohmann/json。不再单列 `preprocess/`（并入 `capture/`）与 `platform/`，两者当前都只有一个变化理由或尚未出现。

## 9. 开发顺序

1. **环境确认**：在实际板端确认编译器、摄像头节点与格式、RGA、NPU 驱动和 Runtime；开发主机准备固定版本的源码、依赖与模型，经 FTP 推送。
2. **单图基线**：独立跑通野火 YOLO26n C++ 例程，再验证自己的工位图片；保存标注图、张量信息与分段耗时，确认实际使用 RGA。
3. **图片检测集成**：在现有骨架中接入日志、配置、硬件构建选项、`RgaPreprocessor` 和 `YoloDetector`；提供图片调试入口，输出项目自己的 `Detection`。
4. **连续检测**：先单独取帧保存图片，再接入 `V4l2FrameSource` 与单线程视觉循环；检查颜色、坐标、帧龄、资源释放和持续运行情况。
5. **工位事件**：完成状态机及脱离硬件的逻辑测试，再接 ROI；用日志验证进入、短暂漏检、离开及再次进入，完成视觉里程碑。
6. **语音闭环**：验证 MeloTTS 与 ALSA 的音质、内存和完整合成耗时，再接模型常驻、音频缓存、问候技能和 TTS 队列。
7. **完整服务**：装配 HTTP、systemd、退出清理与故障观测，完成一小时稳定性和端到端验收。

## 10. 验收标准

## 11. 开发环境与工作流

- 构建位置：全部 C++ 构建在板端进行。板载 GCC 与运行时库天然一致，规避了交叉编译的 sysroot 与 glibc 版本问题。
- 代码同步：源码在开发主机编辑，通过 FTP 单向推送到板端。板端不修改源码，`build/` 不参与同步，避免双向写入冲突。
- 编辑器：VSCode 负责编辑与差异查看。IntelliSense 需要看到板端头文件（`rknn_api.h`、RGA、ALSA、OpenCV），从板端取回一次相关头文件放在 `third_party/sysinclude/`，仅用于补全，不参与编译。
- 交叉编译：不使用。板载编译下编译器与运行时库天然一致；改为交叉编译则需要以板端 rootfs（glibc 2.31）为 sysroot，否则会出现 `GLIBC_2.xx not found`，其收益不足以抵消这部分成本。
- 依赖获取：开发主机可联网，负责获取野火例程、模型转换工具与第三方库源码；板端只接收源码与模型文件。

## 12. 板端环境确认清单

一次性执行并记录结果：

```text
gcc -v ; cmake --version ; ldd --version
aplay -l ; arecord -l
v4l2-ctl --list-devices
dpkg -l | grep -E "libasound2-dev|libopencv|rga|rknn"
dmesg | grep -i rknpu
```

- 声卡：`card 1` 为板载 `rockchip,rk809-codec`，`card 0` 为 HDMI，默认播放路径为 SPK。
- 摄像头：`ov8858` 属受支持的 MIPI 摄像头，实际节点以 `v4l2-ctl --list-devices` 为准；未接摄像头时 `/dev/video0` 也始终存在。
- 若镜像缺少 `libasound2-dev`、OpenCV 开发包、`librga` 头文件或 RKNN 运行时，需在可联网主机下载对应 `.deb` 后经 FTP 安装。
