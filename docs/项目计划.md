# 桌面 AI 机器人项目计划

> 更新时间：2026-09-24

## 1. 项目定位

构建一台部署在桌面上的端侧智能机器人，同时作为持续工作的智能传感器。

- 设备在本地完成感知、事件记录、状态判断和技能执行。
- 端侧优先处理实时、高频和敏感数据，云端只接收必要的结构化摘要。
- 外部模型负责复杂理解和跨事件决策，具体执行由端侧校验并完成。
- 桌面主机可承载本地 GPU 模型推理，作为云端 API 的备用或隐私优先方案。
- 当前先在LubanCat 2 上完成软件闭环，后续接入 Microduck。

核心原则：

1. **本地优先**：断网时，感知和本地技能仍可正常工作。
2. **事件驱动**：所有能力遵循 `Event -> Trigger -> Skill -> Action`；多技能阶段在触发后增加候选技能仲裁。
3. **结构化协同**：上报状态和事件摘要，不上传持续原始数据。
4. **后端可替换**：统一业务请求与结果，由适配层处理云端 API 和桌面 GPU 的协议差异。

## 2. 总体架构

```text
摄像头 / 麦克风 / 环境传感器
              |
              v
       数据采集与预处理
              |
              v
      感知与事件生成模块
              |
              v
     触发器 / 本地状态机
              |
              v
      技能仲裁、调度与执行
          |              |
          v              v
       本地动作      推理后端（可配置）
    TTS / 舵机等     |             |
                  云端 API    本地桌面 GPU
```

本地规则负责确定性判断；外部推理按需异步调用，不阻塞感知。云端 API 是默认协同方式，桌面 GPU 通过适配层提供替代能力。

## 3. 技术栈

| 层次 | 技术 |
|---|---|
| 语言与构建 | C++17、CMake、CTest |
| 系统与运行 | Linux、多线程、systemd、journald |
| 编译方式 | 阶段一采用板载原生编译，不使用交叉编译 |
| 代码同步 | VSCode 编辑 + FTP 单向推送（板端不联网） |
| 第三方依赖 | spdlog、Catch2、cpp-httplib、nlohmann/json 全部 vendor 进仓库 |
| 摄像头 | V4L2、OpenCV |
| 图像加速 | RGA |
| 模型推理 | RKNN-Toolkit2、RKNPU2、YOLOv8n INT8 |
| 语音合成 | RKNN MeloTTS 中文（中英混合） |
| 音频输出 | ALSA |
| 服务接口 | cpp-httplib、nlohmann/json |
| 日志与测试 | spdlog、Catch2 |
| 数据存储 | 后续阶段使用 SQLite |
| 后续扩展 | MPP、云端 API、ESP32、舵机控制 |
| 桌面 GPU 备选 | Ollama、llama.cpp |

约束：

- 核心程序使用 C++，Python 用于模型导出、转换和验证。
- 语言基线取 C++17：板端 Ubuntu 20.04 自带 GCC 9.4。

## 4. 阶段规划

### 第一阶段：端侧单技能闭环

**目标**

在鲁班猫 2 上完成 `greet_at_desk`：检测人员进入工位后，使用本地 MeloTTS 播放一次中文问候。

**主要任务**

- 跑通摄像头、RGA、RKNN、MeloTTS 和 ALSA。
- 建立单进程多线程骨架与按功能点划分的模块边界。
- 完成人体检测、工位 ROI、触发状态机和冷却控制。
- 完成 MeloTTS 音频缓存、失败可观测和本地 HTTP 接口。
- 使用 systemd 常驻，并完成性能与稳定性验证。

**阶段产物**

- 可在 RK3568 上离线运行的 C++ 程序。
- 可重复触发的中文/中英混合端侧问候技能。
- 构建、部署、调试和性能测试文档。

详细实施与验收标准见 [第一阶段计划.md](./第一阶段计划.md)。

### 第二阶段：本地多技能平台

**目标**

将单技能程序扩展为可注册、可配置、可记录事件的本地技能平台。

**主要任务**

- 抽象通用事件、触发器、技能和动作接口。
- 增加久坐提示、喝水提示等本地技能。
- 定义状态快照，区分事实、推断与未知；引入 SQLite，记录事件、决策和有限记忆。
- 增加技能配置、模型按需加载和统一调度；由本地规则筛选候选技能并仲裁，允许暂不执行。
- 完善异常恢复、资源限制和运行观测。

**阶段产物**

- 技能注册、规则仲裁与调度器。
- 至少两个可独立运行的本地技能。
- 状态快照与 SQLite 事件、决策、记忆存储。
- 多技能运行、配置和测试文档。

### 第三阶段：云端与桌面 GPU 协同

**目标**

通过统一业务接口接入云端与桌面 GPU，将有限决策与文本生成分开适配，保持离线本地技能可用。

**主要任务**

- 基于状态快照设计事件摘要、有限决策与文本生成的请求和结果格式。
- 实现云端与桌面 GPU 适配、鉴权和切换；评估 Jev 等可选判断后端，用于语境判断与候选技能选择。
- 实现 Tool Calling、端侧白名单、参数校验和执行确认；确定性约束始终由代码检查。
- 异步推理结果关联事件与快照，设置有效期、执行前条件复核和去重；离线记录可补传，过期动作不补执行。
- 实现超时重试、故障转移和 Token 预算；低置信度或后端不可用时按技能策略回到本地规则或暂不执行。
- 先用 Python 回放标注场景，对比规则、Jev 和本地模型的误打扰率、漏提醒率与 P95 延迟，再决定接入；按后端分别验证阈值。

Jev 仅作为候选 API：当前支持文本/JSON 状态，不承担视觉感知、文本生成或电机控制，不预设可在 RK3568 本地部署。能力以官方文档为准。

**阶段产物**

- 云端 API 与桌面 GPU 共用的模型适配层。
- 结构化事件与端侧技能调用协议。
- 云端不可用时切换本地 GPU 或本地规则的降级机制。
- 后端对照评估及建议、接受、实际执行的关联记录。
- 云端协同、本地 GPU 部署和调试文档。

### 第四阶段：机械载体与低功耗

**目标**

接入 Microduck 兼容机械身体和 ESP32，补齐动作表达与低功耗唤醒能力。

**主要任务**

- 适配 Microduck 兼容硬件和舵机控制。
- 实现点头、移动、转身等动作后端。
- 使用 ESP32 负责语音唤醒、人体接近检测和主控唤醒。
- 协调主控休眠、事件上报和实时技能之间的功耗策略。
- 完成机械动作与语音技能的同步和异常保护；模型只建议技能，端侧负责动作限位与实时控制。

**阶段产物**

- 可替换的机械动作后端。
- 语音唤醒与人体接近唤醒流程。
- 至少一个语音与动作组合技能。
- 功耗、延迟和可靠性测试报告。

## 5. 开发约束

- 每一阶段先完成最小闭环，再增加模型、技能和硬件。
- 新增能力必须经过事件、触发、技能和动作链路，不得直接耦合硬件。
- 所有常驻模型和后台线程都必须有资源上限、错误恢复和可观测指标。
- 外部模型能力始终是可选增强；后端替换须通过同一组场景验证，断网不影响本地闭环。
- 机械硬件使用 Microduck，尽量不重新设计结构。
